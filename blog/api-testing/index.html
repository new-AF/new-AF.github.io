Objectives

We'll be using these packages that were chosen for their DX (developer experience):

  • vitest as test runner, building test cases.

  • supertest for API testing, setting headers and payloads.

Better DX Testing Approach

A tedious and repetitive part of the current approach that doesn't scale is always coming up with unique and descriptive function names (e.g. ts: createUserValid) and having to again replicate the description in ts: it("creates a user with valid fields", createUserValid), example:

TypeScript
1// create a user with valid fields
2const createUserValid = async () => {
3    const response = await request(app)
4        .post("/api/v1/users")
5        // ...
6
7    // resource created
8    expect(response.status).toBe(201);
9    // ...
10
11// top-level describe, repeat same description
12describe("POST /api/v1/users", () => {
13    it("creates a user with valid fields", createUserValid);
14});

Instead we will pursue an approach with better developer experience (DX) that's use easy and equally descriptive, it uses object key names as description, and value as test function, example:

TypeScript
1// all our test cases to be iterated through
2const cases = {};
3
4// create a user with valid fields
5cases["creates valid user, returns 200"] = async () => {
6    const response = await request(app).post("/api/v1/users");
7    // ...
8
9    // resource created
10    expect(response.status).toBe(201);
11    // ...
12};
13
14// top-level describe
15describe("POST /api/v1/users", () =>
16    Object.entries(cases).forEach(([caseName, testFunction]) =>
17        it(caseName, testFunction)
18    ));

The test case that failed is:

  • DELETE /api/v1/users/abc

  • It should return error status code 400 because it is a (Zod) runtime validation error, not 500 an internal server error.

  • This is because we only accept numbers as request parameters (DELETE /api/v1/users/1), not strings.

  • Our error middleware should be activated but is not happening:

    TypeScript

3    // Validation error
4    if (error instanceof ZodError) {

7        response.json({ errors: flattenError(error) });
8        return;
9    }
10
11    // Standard JS Exception

16        return;
17    }
18

Turns out the bug is in the errorHandler function signature: ts: const errorHandler = (error: unknown, response: Response, ) => ...

This is because Express only treats 4-parameter functions as middleware, but we have 2 which means ours is never called.

This means: this whole time we thought our error-handling middleware was registered and would catch errors but it was never called, not even once.

So let's fix our errorHandler function signature to be 4-parameter:

TypeScript
1/* fileName: src/middleware/errorHandler.ts */
2import { Request, Response, NextFunction } from "express";
3import { ZodError, flattenError } from "zod";
4
5export const errorHandler = (
6    error: unknown,
7    _request: Request,
8    response: Response,
9    _next: NextFunction
10) => {
11    // Validation error
12    if (error instanceof ZodError) {
13        // Bad request
14        response.status(400);
15        response.json({ errors: flattenError(error) });
16        return;
17    }
18
19    // Standard JS Exception
20    if (error instanceof Error) {
21        // Internal Server Error
22        response.status(500);
23        response.json({ error: error.message });
24        return;
25    }
26
27    /*
28        Safety net because JavaScript lets us throw literally anything, we must guard against it.
29        e.g. `throw "DB Crashed", throw 1234`
30        Without this fallback, Express would crash or hang if something bizarre was thrown.
31    */
32    response.status(500);
33    response.json({
34        error: "Unknown server error",
35        detail: typeof error === "string" ? error : undefined,
36    });
37};

And voila all our test cases pass!
