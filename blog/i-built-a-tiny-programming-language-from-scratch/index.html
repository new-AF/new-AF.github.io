I Built A Tiny Programming Language from Scratch

(and it can print Hello World with a single variable!)

By: Abdullah Fatota
Last updated: 02 April 2026

Backstory

I built Tiny Lang as my solution to the AdventJS 2025 challenge.

The last challenge (#25) asked to implement a non-Turing complete programming language with an esoteric syntax, very much a simplified version of BrainF---

I further extended my solution by giving it the ability to print, and print it does, the whole Hello World! all with a single variable! 👨🏽‍💻

Playground

You can try Tiny Lang yourself in a simple playground where you can type programs, run them, and instantly see the results (or an infinite loop if you wrote that 😅)

The Challenge

The challenge is to build a interpreter that contains a single counter variable. The interpreter consumes a string of instructions, runs them, and returns the counter value at the end.

Each instruction is a character (length 1 string):

InstructionFunction
+Increments the counter
-Decrements the counter
[whileNonZero opening block.
Run the loop only if the counter is non-zero.
If counter is 0 skip the body, and run the instruction after the closing block ]
]whileNonZero closing block.
If the counter is non-zero loop back and run the body again.
{ifNonZero opening block.
Run the body only if the counter is non-zero.
If the counter is 0 skip the body, and run the instruction after the closing block }
The ifNonZero statement runs at most once, this is in contrast to whileNonZero which can run indefinitely.
}ifNonZero closing block.
Because ifNonZero runs at most once, we simply advance the read head.
>The No Op(eration) instruction.
Does nothing but advance the read head.
Equivalent to a pass in Python
!My own extension to the language 😉
Prints the counter as a single ASCII character.
Does not print a new line.

Printing

To print "Hello World!" we print each letter individually by incrementing or decrementing the counter to the ASCII value, and then calling the print command (!), for example:

  • H is ASCII value 72, so we repeat the increment command (+) 72 times.
  • e is ASCII 101, but because the counter is already at 72, we need only call increment 29 times.
  • and so on...

Interpreter Architecture

To build the interpreter we need to keep track of 2 values, and update them after processing each token:

  1. The counter value.
  2. The read head or tape index, which controls the next token to read from the program tape. It can go backward or forward enabling the looping behavior of whileNonZero and jumping of ifNonZero.

But these are just variables, to implement the actual interpretation algorithm there are 2 approaches:

  • The common mutation approach: we mutate the global variables from inside the loop. The major downside to this approach besides being error-prone: it obfuscates the code logic, it isn't immediately clear what the code is doing.

Or

  • The functional programming (FP) approach: after each token, we get brand new counter and read head values. The major upside is readability and simplicity.

I opted for the FP approach because it provides the best DX for me to write the code and for readers to easily reason about it. So I need to build 3 things:

  1. The Jump Table because it enables whileNonZero looping and ifNonZero jumping.
  2. The Transition Functions, these interpret the actual tokens.
  3. The Main Execution Loop, this is our conductor, it consumes the input program and feeds its tokens to the Transitions Functions.

So let's start backwards:

State and the Main Execution Loop

I grouped the readHead and counter under a simple State object. Under the FP approach, after we process each token, we return a new state. This makes the interpreter architecture easy to reason about.

ts
type State = {
    readHead: number;
    counter: number;
};

let currentState: State = {
    readHead: 0,
    counter: 0,
};
  • readHead controls which token/character to read, enabling us to infinitely go backward or forward in the program.
  • counter is the single counter value, we return it after consuming the entire program.
ts
// run the program the program, as long as there are instructions
while (currentState.readHead < tokens.length) {
    const currentToken = tokens[currentState.readHead];
    const nextState = processToken(currentToken, globalJumpTable);
    currentState = nextState;
}

The Transition Functions implement our interpreter logic for each token, they allow side effects like printing, but always return the next State.

The Main Loop runs the program input by consuming its tokens, calling the appropriate Transition Function, and updating the currentState reference.

Consequently we need 2 passes over the entire program input:

  1. The first pass to build the Jump Table.
  2. The second to run the Main loop.

Tokenization

Tokenization is grouping the source code characters into key constructs of the programming language. For example:

ts
while (condition) {
    counter += 1;
}

The tokens are: while, (, condition, ), {, counter, +=, 1, and }

To us humans especially with syntax highlighting it looks obvious but to computers they require an algorithm to group the characters to tokens.

Fortunately for Tiny Lang each character is a token, however we will still define a custom type Token Object:

ts
enum TokenType {
    Print = "Print",
    Pass = "Pass",
    Increment = "Increment",
    Decrement = "Decrement",
    WhileStart = "WhileStart",
    WhileEnd = "WhileEnd",
    IfStart = "IfStart",
    IfEnd = "IfEnd",
}

// ...

type Token = { type: TokenType; index: number };

// ...

const tokens: Token[] = Array.from(code, (character, index) => {
    // part of tokenization, and for better DX
    const tokenType = {
        "!": TokenType.Print,
        ">": TokenType.Pass,
        "+": TokenType.Increment,
        "-": TokenType.Decrement,
        "[": TokenType.WhileStart,
        "]": TokenType.WhileEnd,
        "{": TokenType.IfStart,
        "}": TokenType.IfEnd,
    };

    const type: TokenType = tokenType[character];

    const token: Token = { type, index };

    return token;
});
  • type is an enum TokenType, this is for robust software engineering and better observability during debugging.
  • We need index in order to construct the Jump Table later.

Building the Jump Table 🔑

Continuing with ++{[-]+}+ as example

When we reach the closing block ] (index 5) we must jump back to the most recent opening block [ (index 3) and continue execution from there by running - (decrement) until the counter is 0.

While we do know the token indicies, how do track the opening and closing positions?

We use a stack and an algorithm similar to the one used to track balanced parenthesis.

The matching pairs are:

  • index 3 -> index 5 (opening block [ -> closing block ]),
  • index 5 -> index 3 (closing block ] -> opening block [) i.e. the looping-back behavior of whileNonZero
  • index 2 -> index 7 (opening block { -> closing block })

For the last case, we don't do the reverse case e.g. (closed block } -> opening block {), because there is no looping back from the end of ifNonZero to the beginning, the block runs at most once.

Once we found all the mappings, we need to store them in an adequate data structure later for retrieval: we use a hash map.

To summerize:

  1. We use a stack to find all the matching opening and closing blocks of whileNonZero and ifNonZero

  2. We use a hash map to store those matching pairs.

ts
//...

/*
    Record locations of WhileStart, WhileEnd, IfStart, IfEnd
    we don't need IfEnd -> IfStart because once if reaches end it cannot loop back
*/
type JumpTable = Map<number, Token>;

// ...

const buildJumpTable = (tokens: Token[]): JumpTable => {
    // match [] {} used to build jump tables
    const stack: Token[] = [];

    const jumpTable: JumpTable = new Map();

    for (const token of tokens) {
        const { type, index } = token;
        if (type === TokenType.WhileStart || type === TokenType.IfStart) {
            stack.push(token);
        }
        // do it both ways, jump[start] = end, and jump[end]=start
        else if (type === TokenType.WhileEnd) {
            const loopStart = stack.pop();

            if (loopStart === undefined) {
                raiseMalformedInput();
            }

            // malformed input
            if (loopStart.type !== TokenType.WhileStart) {
                raiseMalformedInput();
            }

            // in case we need to skip over the loop; jump[start] = end
            jumpTable.set(loopStart.index, token);

            // in case we need to loop back; jump[end] = start
            jumpTable.set(index, loopStart);
        }
        // only one way jump[ifStart] = ifEnd; because we cannot go back/loop
        else if (type === TokenType.IfEnd) {
            const ifStart = stack.pop();

            if (ifStart === undefined) {
                raiseMalformedInput();
            }

            // malformed input
            if (ifStart.type !== TokenType.IfStart) {
                raiseMalformedInput();
            }

            jumpTable.set(ifStart.index, token);
        }
    }

    // malformed input, incomplete closing token e.g. "[+"
    if (stack.length > 0) {
        raiseMalformedInput();
    }

    return jumpTable;
};

During the building attempt if we find a mismatched or missing coding block e.g. programs:

  • {],
  • {,
  • etc

Then we raise an exception by calling raiseMalformedInput (which is later handled by encompassing code like Tiny Lang Playground that shows an informative error badge).

Building the Transition Functions 🔑

ts
// ...

// produce our next state
type StateFunction = (state: State, globalJumpTable: JumpTable) => State;

// ...

const tokenTypeToTransitionFunction: Record<TokenType, StateFunction> = {
    [TokenType.Print]: processPrint,
    [TokenType.Pass]: processPass,
    [TokenType.Increment]: processIncrement,
    [TokenType.Decrement]: processDecrement,
    [TokenType.WhileStart]: processWhileStart,
    [TokenType.WhileEnd]: processWhileEnd,
    [TokenType.IfStart]: processIfStart,
    [TokenType.IfEnd]: processIfEnd,
};

// ...

For each token we construct a handler function that always takes in:

  1. the argument token and,
  2. a reference to the global jump table

The function returns a new State, and can possible do a side effect e.g. printing.

We use a hash map to map the tokens to the function:

Processing !

We convert the numerical representation of the counter to ASCII, we call process.stdout.write if the interpreter runs in Node.js or printFunction supplied by the user.

Finally we advance the read head.

ts
// process "!" print instruction
// side effect: print the single counter as ascii. advance read head.
const processPrint = (currentState: State, _passedJumpTable): State => {
    const { readHead, counter } = currentState;

    // without new line
    const character = String.fromCharCode(counter);

    // external custom accumulating/printing function
    if (printFunction) {
        printFunction(character);
    }

    // otherwise default in Node.js
    else if (typeof process !== "undefined") {
        process.stdout.write(character);
    }

    return { counter, readHead: readHead + 1 };
};

Processing >

We do nothing but advance the read head. The instruction is equivalent to the pass statement in Python.

ts
// process ">" pass instruction
// just advance read head, move to next instruction. we don't need the jump table
const processPass = (): State => {
    const { readHead, counter } = currentState;

    return { counter, readHead: readHead + 1 };
};

Processing +

We simply increment the counter, and advance the read head.

ts
// process "+" increment instruction
// increment current counter, move to next instruction.
const processIncrement = (): State => {
    const { counter, readHead } = currentState;
    return {
        counter: counter + 1,
        readHead: readHead + 1,
    };
};

Processing -

We simply decrement the counter, and advance the read head.

ts
// process "-" decrement instruction
// decrement current counter, move to next instruction.
const processDecrement = (
    currentState: State,
    _passedJumpTable: JumpTable,
): State => {
    const { counter, readHead } = currentState;
    return {
        counter: counter - 1,
        readHead: readHead + 1,
    };
};

Processing [

  • If the counter is 0, we skip the body, and jump to the closing block ]. We do that by consulting the passed global jump table and setting the read head to the matching ] location.

  • If the counter is not 0, we enter the loop body by simply advancing the read head.

ts
// process "[" while start instruction
// if counter is 0, jump to end of loop, otherwise advance read head and enter "body"
const processWhileStart = (
    currentState: State,
    passedJumpTable: JumpTable,
): State => {
    const { counter, readHead } = currentState;

    // jump to end of loop
    if (counter === 0) {
        // malformed input
        if (!passedJumpTable.has(readHead)) {
            raiseMalformedInput();
        }

        const WhileEnd = passedJumpTable.get(readHead);
        const nextIndex = WhileEnd.index;

        return { counter, readHead: nextIndex };
    }

    // else enter the loop, move to next instruction
    return { counter, readHead: readHead + 1 };
};

Processing ]

  • If the counter is 0, we exit the loop body by simply advancing the read head.

  • If the counter is not 0, we loop back to the opening block [. We do that by consulting the passed global jump table and setting the read head to the matching ] location.

ts
// process "]" while end instruction
// if counter is not 0, loop back, jump to "[" beginning
const processWhileEnd = (
    currentState: State,
    passedJumpTable: JumpTable,
): State => {
    const { counter, readHead } = currentState;

    // loop back, jump to loop start
    if (counter !== 0) {
        if (!passedJumpTable.has(readHead)) {
            raiseMalformedInput();
        }

        const loopStart: Token = passedJumpTable.get(readHead);
        const startIndex = loopStart.index;

        return { counter, readHead: startIndex };
    }

    // counter === 0; move to next instruction
    return { counter, readHead: readHead + 1 };
};

Processing {

  • If the counter is 0, we skip the body, and jump to the closing block }. We do that by consulting the passed global jump table and setting the read head to the matching } location..

  • If the counter is not 0, we enter the condition body by simply advancing the read head.

ts
// process "{" if start instruction
// if counter is 0, jump to end of condition, otherwise advance read head and enter "body"
const processIfStart = (
    currentState: State,
    passedJumpTable: JumpTable,
): State => {
    const { counter, readHead } = currentState;

    // jump to if end
    if (counter === 0) {
        // malformed input
        if (!passedJumpTable.has(readHead)) {
            raiseMalformedInput();
        }

        const ifEnd = passedJumpTable.get(readHead);
        const jumpIndex = ifEnd.index;

        return { counter, readHead: jumpIndex };
    }

    // else enter if
    return { counter, readHead: readHead + 1 };
};

Processing }

Since there is no looping back from the end of ifNonZero to the beginning, we simply advance the read head.

ts
// process "}" if end instruction
// "if" cannot loop back, so just advance read head
const processIfEnd = (
    currentState: State,
    _passedJumpTable: JumpTable,
): State => {
    const { counter, readHead } = currentState;

    return { counter, readHead: readHead + 1 };
};

Time Complexity

Our entire solution, both interpreter construction and running the input program has time complexity:

O(n) + O(T) or O(n + T)

  • n is the input string length, or equivalently program size or tokens count.
  • T is the number of instructions encoded in the program itself.

O(n) is the work done building the interpreter including the Jump Table, and it's proportional to the count of tokens that make up the static program.

O(T) is the work done by the interpreter which reflects the behavior of the encoded program itself.

If the program encodes a linear algorithm, our interpreter will run in linear time. If the encoded algorithm is exponential our interpreter will take exponential time to complete. If the program encodes an infinite loop, our interpreter will never halt.

In short the Time Complexity is work done by processing the input in addition to the growth behavior of the encoded program itself.

Space Complexity

Our entire solution, both interpreter construction and running the input program has space complexity:

O(n)

With n being the input string length, or tokens count.

Or equivalently work proportional to the program size.

Relation to BrainF---

As mentioned previously although the challenge was heavily inspired by the esoteric language, Tiny Lang is not Turing-complete because that requires at least two counters, while BrainF--- can run any arbitrary function i.e. it is Turing-complete.

Conclusion

I implemented a tiny programming language similar to BrainF---, while we cannot program any arbitrary (Turing) program, nonetheless we were able to print Hello World! all with a single variable!
