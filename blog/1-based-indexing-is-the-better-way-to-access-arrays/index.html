1-based Indexing Is The Better Way To Access Arrays

(In Higher-level Programming Languages)

By: Abdullah Fatota
Last updated: 02 April 2026

You might be thinking how dare I call myself a software engineer if I think Zero-Based Indexing (ZBI) is a bad idea?

Well I'd argue for high-level programming languages like JavaScript, ZBI is only a convention, and a bad one at that, which we copied from C that we absolutely did not have to do.

It leads to:

  • Worse developer experience,
  • Worse code readability and consequently,
  • More bugs (off-by-one)

You want to tell me that:

  • 0 denotes the first element.
  • 1 denotes the second element.
  • length - 2 denotes the before-last element and
  • length - 1 denotes the last element

Why is it off by 1?

Why are we doing this to ourselves?

Objectively your dev experience would be much better if you used your human convention that you've been using your whole life without any issues:

  • 1 to denote the first element
  • 2 to denote the second
  • length - 1 to denote before-last element and
  • length to denote the last element

That's One-Based Indexing (OBI)

Proof

Boom.

Developer Experience (DX)

I wrote 2 versions of Bubble Sort using both indexing schemes, and it is objectively clear which is less prone to off-by-one errors but is also easier to understand.

1-Based Bubble Sort

bubble-sort-1-indexing.mjs
// check Appendix
import { accessArray, setArray } from "./1-indexing-utils.mjs";

const test = [6, 5, 4, 3, 2, 1];
const testEmpty = [];

export const bubbleSort = (arrayOriginal) => {
    const array = [...arrayOriginal];
    const length = array.length;

    // runs as long as there are at least 2 elements [1,2]
    for (let outerIndex = length; outerIndex >= 2; --outerIndex) {
        for (let index = 1; index < outerIndex; ++index) {
            const elementFirst = accessArray(array, index);
            const elementSecond = accessArray(array, index + 1);

            if (elementFirst <= elementSecond) continue;

            setArray(array, index, elementSecond);
            setArray(array, index + 1, elementFirst);
        }
    }

    return array;
};

console.log(bubbleSort(test)); // [ 1, 2, 3, 4, 5, 6 ]
console.log(bubbleSort(testEmpty)); // []

0-Based Bubble Sort

bubble-sort-0-indexing.mjs
const test = [6, 5, 4, 3, 2, 1];
const testEmpty = [];

export const bubbleSort = (arrayOriginal) => {
    const array = [...arrayOriginal];
    const length = array.length;

    // runs as long as there are at least 2 elements [1,2]
    for (let outerIndex = length - 1; outerIndex >= 1; --outerIndex) {
        for (let index = 0; index < outerIndex; ++index) {
            const elementFirst = array[index];
            const elementSecond = array[index + 1];

            if (elementFirst <= elementSecond) continue;

            array[index] = elementSecond;
            array[index + 1] = elementFirst;
        }
    }

    return array;
};

console.log(bubbleSort(test)); // [ 1, 2, 3, 4, 5, 6 ]
console.log(bubbleSort(testEmpty)); // []

The Real Difference

The real difference is in the outer loop:

mjs
    // 1-based
    for (let outerIndex = length; outerIndex >= 2; --outerIndex) {
        for (let index = 1; index < outerIndex; ++index) {

mjs
    // 0-based
    for (let outerIndex = length - 1; outerIndex >= 1; --outerIndex) {
        for (let index = 0; index < outerIndex; ++index) {

The 1-based indexing version is meant for humans and hence is easier to understand:

  • the outer loop runs backward from the last element length
  • to (and including) the second element outerIndex >= 2.

Even if I were to re-write the outer condition as outerIndex > 1 it would still be easy to understand: the outer loop would not process the first element.

Most importantly however, I would be confident modifying the loop bounds as the algorithm requires without worrying about off-by-one errors because 2 unequivocally means the second element, not the third.

The 1-based version is superior because it aligns with and centers the human experience.

The 0-based version, however, introduces friction and second-guessing into the picture which always degrades the dev experience.

mjs
    // 0-based
    for (let outerIndex = length - 1; outerIndex >= 1; --outerIndex) {
        for (let index = 0; index < outerIndex; ++index) {

This is because You and I would be constantly second-guessing our intuition as to what these numbers represent, trying to context-switch to a different mental model when dealing with arrays, but then switch back to our "normal" brain mode for all the other programming constructs. All of this context-switching is mentally exhausting and error-prone.

  • In this version the outer loop runs backward from the last element length-1
  • to (and including) the second element outerIndex >= 1. Here 1 here denotes the second element.

It would still be problematic if I were to re-write the outer condition as outerIndex > 0. This is supposed to convey the same meaning, that the outer loop would not process the first element. Here 0 here denotes the first element.

Caveat

My article only applies to high-level programming languages. The one place where ZBI makes sense is in low-level languages like C that directly access memory because of how pointer arithmetic and offsets work, but otherwise we should not copy C in this regard.

Appendix

1-indexing-utils.mjs
// allowed indices: [1 - length], inclusive
export const arrayIndexWithinBounds = (array, index) => {
    if (Array.isArray(array) === false) return false;

    if (index < 1 || index > array.length) return false;

    return true;
};

// get element, 1 based indexing
export const accessArray = (array, index) => {
    if (arrayIndexWithinBounds(array, index) === false) return undefined;

    return array[index - 1];
};

// set position, 1 based indexing
export const setArray = (array, index, newElement) => {
    if (arrayIndexWithinBounds(array, index) === false)
        throw new Error("Array index out of bounds");

    array[index - 1] = newElement;
};
