I Built the Backbone of Apps and Web Services: A CRUD Service

Abdullah Fatota
Updated: 21 August 2026

Overview

For Week 2 Assignment of my Backend Engineering Internship, I built what most internet Apps are made of: A CRUD service.

I built a backend service that keeps track of To-do tasks by the user. It allows the user to:

  • Create tasks

  • Mark them as done

  • Edit their content

  • Delete them

CRUD

CRUD is an acronym for (Create, Read, Update, Delete).

They are abstract operations that most backend services implement to do useful things.

Because the internet uses the HTTP protocol, we'll implement CRUD using specific requests called HTTP Methods.

To recap:

  • CRUD are abstract operations on data

  • HTTP Methods are specific protocol messages we'll use to to implement CRUD operations

HTTP Methods

The internet is built on HTTP. It is a message-passing protocol between a Client and a Server.

The protocol's syntax is plain text, and has the following form:

HTTP
MethodName URL HTTPVersion
MetaHeaderName: MetaValue
...

OptionalRequestBody

To convey intent to the server, the Client has several message types or methods to choose from.

  • GET to retrieve information from the server.

  • POST to perform some action on the server, e.g. create User, Task, etc.

  • PUT to edit an already existing resource on the server.

  • DELETE the resource.

Example:

To create a task on the server, we send POST with a JSON request.

HTTP
POST /tasks HTTP/1.1
HOST: my-backend-internship-week-2-assignment-1.onrender.com
Content-Type: application/json

{"title": "Buy milk"}

Getting a specific task

We search for the Task which matches the id we were sent in the search parameter.

On success we send status 200 OK and the JSON Task

Otherwise on error we send 404 Not Found and error JSON.

Creating a Task with POST

First we have to validate the incoming JSON task:

  1. it must have a title key

  2. title must be a string

TypeScript
1app.post("/tasks", (request, response) => {
2    const { body } = request;
3
4    // validate title
5    const { success, error } = validatePOST(body);
6
7    // bad request
8    if (!success) {
9        response.status(400);
10        response.json({ error });
11        return;
12    }
13
14    // create it
15    const { title } = body;
16    const id = storedTasks.length + 1;
17
18    const task = {
19        id,
20        title,
21        done: false,
22    };

24    storedTasks.push(task);

26    response.status(201);
27    response.json(task);

The validation logic:

17

21const validatePOST = (body): ValidationResult => {
22    if (!body) {
23        return { success: false, error: "Missing body" };
24    }
25
26    const { title } = body;
27
28    const titleResult = validateTitle(title);
29
30    if (!titleResult.success) {
31        return titleResult;
32    }
33
34    return { success: true };

In case of success, status 201 Created is returned, otherwise 400 Bad request and error JSON explaining what went wrong.

By default the task is marked as not done, this is changed later by a PUT request.

Updating Task status with PUT

A PUT request updates both "title" and "done" of a Task on the server, it needs the request JSON with those values.

Additionally, it needs the id of the Task to update.

TypeScript
1app.put("/tasks/:id", (request, response) => {
2    const { body } = request;
3
4    const { id: stringId } = request.params;
5
6    const id = Number(stringId);
7
8    const { success, error } = validatePUT(body);
9
10    // bad request
11    if (!success) {
12        response.status(400);
13        response.json({ error });
14        return;
15    }
16
17    const { title, done } = body;
18
19    const found = storedTasks.find((obj) => obj.id === id);
20
21    if (!found) {
22        response.status(404);
23        response.json("Not found");
24        return;
25    }
26
27    // enforces idempotancy: same content leaves same object
28
29    if (found.title !== title) {
30        found.title = title;
31    }
32    if (found.done !== done) {
33        found.done = done;
34    }
35
36    response.status(200);
37    response.json(found);
38});

POST vs PUT

A Common backend interview question that's often asked is:

What's the difference between POST and PUT?

  • POST performs an action, like creating Users. While PUT updates them (by convention).

  • POST is Non-idempotent, PUT is Idempotent. (👈🏽 This is what they're looking for)

Idempotency

Idempotency ("the same power") is the property of an operation where applying it multiple times produces the same result as applying it once.

In the context of POST vs PUT: Sending multiple PUT requests is equivalent to sending it once.

It results in the same final state on the server.

For an analogy think the elevator button:

Pushing the button 1000 times will not make the elevator come any faster than pushing it once. That's PUT logic.

If it were a POST request, the server is allowed to accelerate bringing the elevator because clearly the user is in a hurry.

Another common scenario is Money.

  • During online transaction processing if the same request to charge you money is sent multiple times, often due to network issues, then an idempotent API guarantees you only will be charged once, not multiple times.

Deleting tasks with DELETE

We simply look for the Task that has the id sent, and remove it.

If the delete is successful we return status 204 No Content because there's no body to return.

TypeScript
1app.delete("/tasks/:id", (request, response) => {
2    // debugger;
3
4    const { id: stringId } = request.params;
5
6    if (!stringId) {
7        response.status(400);
8        response.json({ error: "missing id to delete" });
9    }
10
11    const id = Number(stringId);
12
13    const foundIndex = storedTasks.findIndex((obj) => obj.id === id);
14
15    if (foundIndex === -1) {
16        response.status(404);
17        response.json({ error: "not found id to delete" });
18    }
19
20    // delete element
21    storedTasks.splice(foundIndex, 1);
22    response.status(204);
23    response.send();
24});

In case of error we return status 404 Not Found
